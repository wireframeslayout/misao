# Rust implementation

[English](../en/rust.md) | [日本語](../ja/rust.md)

misao's daemon and CLI are being rewritten in Rust as a single `misao` binary, distributed through
GitHub Releases. The SDK (`@misao/sdk`) and the protocol (`@misao/protocol`, `PROTOCOL_VERSION`
0.3.0) stay in TypeScript and the protocol does not change. The Rust build now passes the whole
existing e2e suite (`packages/e2e`) and the CLI tests (`packages/cli/test`), except the opt-in Claude / Codex / systemd cases, on Linux and macOS (arm64 and x64);
on Windows (x64) the e2e suite runs with its POSIX-only cases branched (stage 5, below).
Until binary distribution and the switch in AZITO (#44), the Node build stays the official one.

Related documents: [Protocol](../protocol.md), [CLI](../cli.md), [Configuration](../config.md).

## Layout

```text
Cargo.toml              workspace (resolver 3, edition 2024, MSRV 1.88, shared lints)
rustfmt.toml  clippy.toml  deny.toml
crates/
  misao-protocol/       wire types: JSON-RPC, ErrorCode, ServerInfo, NDJSON framing
    schema/protocol.json  JSON Schema exported from the Zod schemas (generated, committed)
    tests/schema_conformance.rs
  misao-daemon/         daemon core: socket, pid file, logger, connections, RPC, workspaces / windows / panes, PTY, rings, events,
                        screen (terminal emulation), activity detection (state-tracker, profiles), foreground process,
                        per-OS parts: the endpoint (Unix socket / named pipe), the process tree (process group / Job Object), Windows ACLs
    tests/fixtures/node-diff/  inputs and expected values of the Node differential tests (generated by `scripts/gen-rust-diff-fixtures.mjs`)
  misao/                the binary: every CLI subcommand (argument parsing, client, terminal handling for attach), config, socket path
```

Dependencies point one way: `misao` -> `misao-daemon` -> `misao-protocol`.

## Build and test

```bash
cargo build --workspace            # target/debug/misao
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
cargo deny check                   # licenses, advisories, sources (see deny.toml)
```

Policy: stable Rust, MSRV `1.88` (`workspace.package.rust-version`, checked in CI by the `Rust (MSRV)` job),
`unsafe_code = "deny"` (only the small modules that call OS APIs directly allow it, each `unsafe` block with a `SAFETY:` comment: macOS `waitid`, and on Windows the Job Object, ACLs, console modes, stop event, user name), clippy `all` denied, and `unwrap` / `expect` denied outside tests.
`Cargo.lock` is committed and CI uses `--locked`.

Run the Rust daemon by hand:

```bash
target/debug/misao serve --socket /tmp/misao-try/misao.sock --data /tmp/misao-try
```

## Stage 2 behaviour (differences from the Node build)

Error codes and numbers, ordinal renumbering, `ephemeralEnv` (never stored), the child's inherited env
(the daemon's env minus `TMUX*` / `STY` / `ZELLIJ*`, plus `MISAO_SOCKET` / `MISAO_PANE_ID` / `TERM` /
`COLORTERM`), the ring defaults, the meaning of gap / epoch / since, one events stream per connection and
`daemon.started` being event 1 are the same as in the Node build. The differences:

- **A pane that fails to start is not created.** For a missing command or a `cwd` that is not a directory,
  the Node build (node-pty) creates a pane that exits with code 1; the Rust build fails `pane.open` with
  `InvalidParams` (`spawn failed: ...`) and leaves no workspace or pane behind (the Node build treats an
  exception from the `Pane` constructor the same way).
- **Live line subscribers are waited for.** The Rust daemon processes output faster than the Node one, so a
  subscriber that is reading but slower than the child (the SDK, for example) gets overtaken by the 4 MiB
  ring and cut off. While a subscriber lags behind by more than half the ring capacity, the daemon stops
  reading the pty, which blocks the child's writes. A subscriber whose cursor has not moved for one second
  is not waited for: as before, it is cut off once the ring overtakes it, and told through a gap. Nothing is
  waited for while a pane is closing or after its child has exited.
- **`pane.close` leaves no child behind.** On Unix it sends SIGHUP to the process group, then SIGKILL after
  3 seconds (as the Node build does). In addition, if the leader exits on SIGHUP while other processes in
  the group survive (children that ignore SIGHUP, say), they are killed with SIGKILL after the grace period
  before the call returns. The same steps apply to a pane whose leader has already exited but whose group still has survivors (on
  `pane.close` and on daemon shutdown). **Guarding against pgid reuse**: on Linux the leader's exit is detected with `waitid(WNOWAIT)` without reaping it, and the exit code and signal are recorded then.
  The leader stays a zombie until `pane.close` / shutdown has cleaned up the group and only then is reaped, so its pid (= pgid) cannot be reused before
  close, and close can check on the spot, by scanning `/proc` (the zombie leader is not counted), whether the group still has members. An exited pane
  therefore keeps one zombie until it is closed. macOS does the same (stage 5): the leader is waited for with libc's `waitid(P_PID, ..., WEXITED | WNOWAIT)` (the macOS `waitid(2)` has `WNOWAIT`; nix does not wrap it there), the zombie leader is held until close, and
  group membership is read with `ps -A -o pid=,pgid=,stat=` (a zombie `Z` is not counted) instead of `/proc`.
  On Windows the process tree is a Job Object: the child is put in it right after `CreateProcess` and close is `TerminateJobObject`; there is no SIGHUP-style grace period, and survivors of an
  already exited pane are found from the Job's active-process count (details in the stage 5 section).
- **The input queue is bounded.** `pane.write` input is written to the pty by a dedicated thread, so it piles up when the child does not read. Once more than 4 MiB is pending, the Rust build refuses further input immediately with `-32603` (`pane input queue is full ...`) instead of waiting (one write into an empty queue is accepted even if it is larger). The Node build (node-pty) queues without limit and has no equivalent error.
- **`dataB64` in `pane.write`**: invalid base64 is `InvalidParams` (Node's `Buffer.from` silently drops it).
- **Size**: cols / rows keep the whole range Zod allows (safe integers) and `pane.info` and events report the original values; only the value passed to the pty is clamped to 65535.
- **Not implemented**: `preplace` (unimplemented in the Node build too). Persistence and attach arrived in stage 4 (below).
- The child may get a `SHELL` variable (portable-pty fills it in).

## Stage 3 behaviour (screen and activity detection)

`pane.screen`, the `title` / `agentState` / `decidedBy` / `fgCommand` fields of `pane.info`, and the `pane.title` / `pane.state`
events are in. The screen text, cursor and title, and the activity transitions with their times, are checked against the Node build
on recorded output (next section).

### The screen model

Terminal interpretation (the `@xterm/headless` role) is a screen built on the `vte` parser with the semantics of xterm.js 6's
`InputHandler` / `Buffer`: cursor movement, erase, line / character insert and delete, scroll regions, the alternate screen, tab stops,
character sets, wide and combining characters, and reflow of wrapped lines on resize. It does not handle colours / attributes, the mouse or replies to
queries (the Node build does not send xterm's replies to the child either).

`alacritty_terminal` was tried first and rejected. Compared with xterm.js on random control sequences it differed in the cursor column after `IL` / `DL`, in
telling an "empty cell" from "a cell with a space written" (whether trailing spaces are kept), in the cursor column while a wrap is pending at the right
edge, and in the character-width table (xterm.js defaults to Unicode 6, where an emoji is one column). These are differences in internal state, not
fixable by wrapping its `Handler`. The width table is exported from `@xterm/headless` by `scripts/gen-unicode-width.mjs`
(`unicode_width_table.rs`; `npm test` detects staleness).

Differences from the Node build (xterm.js):

- **Size cap**: the protocol accepts safe integers, but the screen model clamps to 1024 x 1024 (each cell costs memory). `pane.info` and events report the original values. The lower bound is xterm.js's 2 columns x 1 row.
- **Sequences not handled**: `CSI Ps SP @` / `A` (horizontal scroll), `CSI Ps ' }` / `~` (insert / delete columns), `CSI t` (off by default), DCS, and colour / attribute / mouse / hyperlink sequences. They do not affect the screen text, or are off by default in xterm.js too. 8-bit C1 controls (U+0080-009F) are treated as characters, not controls. OSC takes at most 16 parameters (a vte limit).
- **xterm.js internal inconsistencies that are not reproduced**: xterm.js throws on `ED 1` at the end of the last line (the Rust build does nothing). After resizing an empty alternate screen and then using it, xterm.js's line list and `ybase` disagree and it reads stale lines outside the screen. When the scrollback is full and a narrowing reflow needs more lines than the list can hold, the result depends on the internal rotation of xterm.js's ring buffer (the Rust build drops the oldest lines). All of these were found in about 0.1% of the differential test's random inputs, in edge behaviour with tiny scrollbacks and widths around 5.
- **Limits on combining marks and REP**: a cell takes at most 32 combining marks (extra ones are dropped; xterm.js has no limit, but a long run of marks would slow row updates down). `CSI Ps b` (REP) repeats at most as many times as the screen has cells (more gives the same screen).
- **OSC length limit**: `vte` buffers an OSC without limit when its `std` feature is on. The `std` feature stays, and OSC length is counted before the bytes reach the parser (`screen_osc.rs`). At 1 MiB it injects CAN to abort the OSC and drops the rest up to the terminator. An aborted OSC does nothing (as xterm.js discards an over-long OSC); the title is never truncated. An OSC cancelled by CAN / SUB in its body does nothing either (`vte` dispatches before cancelling, so the dispatch is discarded while the single cancelling byte is fed). An 8-bit ST (U+009C = `C2 9C`) inside an OSC terminates it like `ESC \` (a `C2` followed by another byte stays part of the content). xterm.js's limit is 10 MB, but real OSCs (titles and so on) are a few KB.
- **Repair of a line list that is too short**: when an unusual sequence of operations leaves the line list shorter than the visible rows, it is padded with blank lines (the clean-up after "xterm.js internal inconsistencies that are not reproduced" above, so that screen operations always hold).
- Screen rows follow xterm.js: spaces that were written are kept, erased cells are dropped from the end of the row.

### Activity detection

The order exit > profile > title > bytes is unchanged. The constants are the Node build's: bytes (3 s window, 200-byte threshold, 2 consecutive ticks,
5 s of quiet for idle, 500 ms input / 800 ms resize grace), title (a title that starts with a spinner glyph and a space; no opinion after 3 s without an update; a non-empty
plain title after a spinner was seen is idle), and the profile's screen judgement (wait 120 ms for output to settle, judge within 300 ms of the first
update). Differences:

- **No timers**: `StateTracker` takes the time (milliseconds since the pane started) as an argument and reports its next deadline with `next_deadline`. A per-pane
  detection thread (`pane_observer`) sleeps until the deadline and calls `advance`. The same input sequence always produces the same transitions, so the
  differential test runs on virtual time. Deadlines at the same time run in the order they were registered.
- **No profile failure handling**: in the Node build `classify` is a function supplied from outside, so a pane that threw three times in a row lost its profile. Rust rules are data and evaluation cannot fail; they are validated (regular expressions and so on) at load time, and a broken one fails startup.
- **Order of output and resize**: terminal parsing happens outside the ring-buffer lock, so a per-pane ordering lock (order -> inner -> observer) applies ingesting output (store and parse) and resizes to the screen in the order they were received.
- **`prev` of `pane.state`**: on exit it is now the actual previous state (stage 2 hard-coded `unknown`). The order `pane.exited` then `pane.state(exited)` is unchanged.

### Profiles (the Claude / Codex rules)

The Node build's `AgentProfile` is only a plug-in point and ships no Claude Code / Codex rules (`misao serve` judges with the generic title / bytes rules only).
The Rust build keeps rules as data (`crates/misao-daemon/src/profiles/*.json`), ported from AZITO's screen rules (`agentScreenRules`).
**`misao serve` uses the bundled profiles by default** (an intentional difference from the Node build). A profile is chosen from the pane's start command and the foreground program;
`decidedBy` is then `claude` / `codex` and `blocked` is possible.

- **Start command**: the executable name (after skipping a leading `env` and its options and `NAME=VALUE` words; `.exe` is dropped case-insensitively) is `claude` or `codex`. When the command is handed to a shell as a string, as in `sh -lc "cd d && claude --x"`, each command in that string (the first word after splitting on `&&` `||` `;` `|` `&`, skipping `exec` and `NAME=VALUE`).
- **Foreground program (`fgCommand`)**: one sampler per daemon (`foreground_sampler.rs`) checks, at an interval (1 s on Linux, 5 s on other Unixes, which use `ps`), the panes whose profile the start command alone does not settle (shells and the like; a pane that started `claude` directly is skipped) in one batch (a single `ps` for all panes on macOS), hands the result to each pane, and the profile is switched the profile **only when the chosen profile changes**. If you start an interactive shell and then run `claude`, the claude profile is attached as soon as `claude` is in the foreground and dropped when the shell is back. A foreground program that has a profile wins; otherwise the start command decides. When the start command is a shell and the foreground is some other program (for example `git` after `claude` exited), there is no profile.
- **What the state-tracker does on a switch**: gaining a profile keeps the current state and schedules a screen judgement (the result arrives within 120 ms); the title / bytes history is kept. Losing it discards the profile's opinion and re-decides from the title / bytes stages only; if none has an opinion the state becomes `unknown` / `none`. The final decision is made once, so exactly one `pane.state` event is emitted (no intermediate `unknown`).

A rule is `{id, verdict, priority, region, when}`. The screen is split into above / prompt box / below by Claude Code's input box (two `─` rules and what is between them),
`region` (`above` / `prompt_box` / `below` / `all` / `title`) names what a rule reads, and `when` combines `all` / `any` / `not` / `contains` (a lower-case substring) /
`matches` (a regex) / `line_matches` (a regex per line) / `last_lines` (the last n lines). The matching rule with the highest priority wins. The verdicts `skip` (the screen
switched to another view) and `error` (stopped by an API error) give no opinion (the title / bytes stages decide) but still silence lower-priority rules. AZITO's `skip`
means "keep the previous state", whereas "no opinion" from a misao profile falls through to the next stage, so that part differs.
Codex's `Action Required` title is a rule with `region: title`.

### Foreground process (`fgCommand`)

Only running panes have it. On Linux it comes from `/proc/<pgid>/cmdline` of the pty's foreground process group leader (the script or module name for an interpreter, as in the Node build).
On macOS it is the executable name of that leader from `ps -o comm=` (like node-pty's `process` in the Node build; never a script name). On Windows ConPTY has no foreground process group and
reporting nothing beats reporting a wrong name, so it is absent (as in the Node build).

`pane.info` / `pane.list` are assembled (including the foreground process lookup) after the global lock is released; under the lock only a snapshot of location, labels and `Arc<Pane>` is taken. On macOS the foreground names for a `pane.list` are fetched with one `ps -o pid=,comm= -p a,b,c` call for the whole list.

## Stage 4 behaviour (persistence, attach, CLI)

### Saving and restoring state

`persistence.json` (in `--data`, or the socket's directory) has **the same format as the Node build and each can read the other's file**
(`packages/e2e/test/persistence.test.ts` checks Node-saved -> Rust-restored and Rust-saved -> Node-restored). It holds the workspace / window
definitions and the pane metadata (`paneId`, `windowId`, `cmd`, `cwd`, `env`, `labels`, `cols`, `rows`); `env` is only the `env` of `pane.open`
(`ephemeralEnv` is never saved). It is written as: a randomly named temporary file in the same directory created with `O_EXCL`, `O_NOFOLLOW` and mode 600, then write -> fsync the file -> rename -> fsync the parent directory
(the Node build writes a fixed-name temporary file and only fsyncs and renames; it has no directory fsync, `O_EXCL` or `O_NOFOLLOW`).
A failure before the rename is undone, but **a failure of the parent-directory fsync after the rename is not** (the file already has the new content, so it counts as success and a warning is logged; on filesystems without directory fsync, EINVAL / ENOTSUP, it is silently a success).
At startup the data directory (`--data`) must be owned by the current user, not a symlink, a directory, and not writable by group / other; a violation stops startup (the Node build does not check).
An existing 0755 directory is accepted (files inside are created 600, so read permission is no concern). The socket directory still has to be 0700.
Loading opens with `O_NOFOLLOW`, requires a regular file of at most 32 MiB, and then reads it. At most 10,000 workspaces, windows and panes each, 4096 entries in each of `cmd` / `env` / `labels`, and 1 MiB per string are accepted;
a larger file stops startup. Saving refuses the same limits (it never writes a file it could not load), so a `pane.open` that hits a limit is undone like any save failure (the Node build has none of these limits).

- **Restart**: saved panes come back as `stopped` (`pid` is `null`, `agentState` is `unknown`). Labels can be edited and `pane.close` works;
  `pane.write` / `resize` / `screen` / `attach` / `subscribe_lines` return `PaneExited` (`pane is stopped`). They count in `paneCount` and `pane.list`.
- **Broken file**: startup fails with `invalid persistence file <path>: <detail>` (no pid file is left): `version` other than 1, missing or extra fields, non-positive `cols` / `rows`,
  malformed ids, duplicate workspace names / window ids / pane ids, a pane in an unknown window. The detail text comes from serde, not Zod.
- **When it saves**: `pane.open` / `pane.close` / `pane.set_label` and workspace / window create, rename, close save first and then emit events.
  Create, rename and labels are undone if saving fails. A `pane.open` whose save fails undoes the layout and the registration and stops the started child without emitting events.
  `close` has already stopped the child, so it is not undone: memory keeps the real state, `pane.closed` is emitted, and then the failure is returned. Sizes (`cols` / `rows`) are saved after a 1 s delay, failures are only logged, and the rest is saved when the daemon stops. A reservation made while a save is in flight is detected with a generation number and saved by the next save instead of being dropped.
- **Exclusion (difference from the Node build)**: the Node build is single-threaded, so "change -> save -> undo on failure" cannot be interleaved. The Rust build runs operations that change saved state one at a time under a `gate` (an async mutex)
  and fsyncs outside the global state lock (reads and I/O do not wait). The snapshot is taken after the write-ordering lock is held, so an old state never overwrites a newer one. Lock order: gate -> write -> global state.

### Attach and multiple clients

`pane.attach` (`mode: raw`, `replay: raw | snapshot | none`) and `pane.detach` keep the Node contract. The replay is sent after the reply, and the boundary is `head`
(the destination is registered and `head` is read under the same lock that ingests output, so there is neither a gap nor an overlap between the replay and live output).
`raw` replays the whole raw ring (`truncated` says whether the ring has a gap); `snapshot` is one notification (`replay: "snapshot"`) that repaints the visible rows; `mode: cells` is `Unsupported`.
The pane size is the last acting client's (`clientId` of `pane.write`, the size of `pane.attach` / `pane.resize`); when the owner leaves, it returns to the last acting remaining client.
A closed connection is cleaned up the same way. Attach, detach and close update the pane-side destination, the connection-side map, `clients`, the size owner and the "closing" mark as one linearization point under the pane's `order` lock (including the registration on the connection side); a failed attach leaves the old attachment on both sides, and an attach after a close has started is refused with `PaneExited` (`pane is closing`).
A message that would take the send queue past 16 MiB is not queued and the connection is dropped (one message cannot jump over the limit). Output buffered for an attach before its reply is also capped at 16 MiB; beyond that the attach is abandoned and the connection dropped.
A snapshot is a single notification. The screen is at most 1024 x 1024 cells: text only is about 1 MiB (about 1.4 MiB in base64), but a worst-case screen where nearly every cell changes colour or decoration (up to about 60 bytes of SGR per cell) can exceed 16 MiB.
Then the rule above drops the connection and the client re-attaches with `replay: none` or `raw`. Real screens (hundreds by tens of cells) are far below 1 MiB. Re-attaching with the same connection and `clientId` only swaps the destination, with no `client.detached`.

Difference from the Node build: closing a pane emits `client.detached` for its clients, but no `pane.resized` for a size hand-over (resizing a pane that is being closed is pointless).

#### Snapshot (colours and decorations)

The screen model used to hold text only. For snapshots to reproduce the look, cells now carry attributes (bold, dim, italic, underline, blink, inverse, invisible, strikethrough; foreground and background: 16 / 256 / RGB)
(a cell grows from 16 to 24 bytes). `CSI m` (both `;` and `:` forms), background-colour erase (BCE), insert / delete / scroll, alternate screen initialisation, cursor save / restore and resets follow xterm.js.
Input modes (application cursor keys / keypad, bracketed paste, focus reporting, mouse reporting) are kept and restored at the end of the snapshot. Like the Node build, the cursor visibility and the scroll region are not restored.
The differential tests compare the snapshot string with the Node build's `serializeSnapshot` **exactly** (the `snapshot-look` scenario and the random scenarios with colours). xterm.js quirks that were matched:
only `CSI T` does not carry the background colour into the erased line, alternate-screen rows are created with the erase attribute, `CSI 38:2:r:g:b` reads r as the colour space, typing in insert mode fills the gap with the current attribute.
Of 4000 extra random scenarios, 3 differ in the screen text (0.1%, the "internal state that is not reproduced" of stage 3) and 1 differs only in attributes (xterm.js mixes up attributes in one reflow case).

### CLI

Every `misao` subcommand (`ls`, `attach`, `new`, `kill`, `status`, `send`, `screen`, `tail`, `events`, `label`, `schema`, `serve`) has the same output format, exit codes, (Japanese) messages, `--json` output and `--help` text as the Node build.
The reference is the Node source and its tests. Argument parsing is **hand-written** to behave like `util.parseArgs` in strict mode (clap is not used, so that error text, exit code 2 and `--json` errors match exactly).
The CLI uses a tokio client (one actor owns the connection and applies a subscribe reply before the replay notifications; it reconnects with the SDK's exponential backoff and restores `since` / `epoch`),
and `attach` puts the terminal in raw mode and handles the prefix-key state machine, SIGWINCH, termination signals and restoring the terminal (`TTY_RESET`) (Unix only; other OSes come later).
Differences: a panic during raw mode restores the terminal, prints `[misao] 予期しないエラー` and exits 1 (Node's `uncaughtException`), unknown keys under `keys` / `rings` in `misao.json` are warnings (as in Node).

`misao.json` (`socket` / `logLevel` / `scrollback` / `rings` / `keys`), the limit defaults and logging (`[misao <ISO time>] msg` on stderr) validate and default like the Node build.

## Stage 5 behaviour (macOS and Windows)

### macOS (arm64 and x64)

Built and tested by CI on `macos-14` (arm64) and `macos-15-intel` (x64): `cargo test`, the whole e2e suite and the CLI tests pass on both.

- **pgid reuse guard** (the carry-over from #40): the leader is not reaped at exit. `waitid(WNOWAIT)` exists in macOS' libc, so the daemon calls it directly (`pty_unix.rs`, the only `unsafe` there), keeps the zombie leader until `pane.close` / shutdown has cleaned up the group, and then reaps it. Its pid (= pgid) cannot be reused before that, so the signal sent at close cannot hit an unrelated group. Linux does the same through nix. The alternatives (kqueue `EVFILT_PROC`, checking the group members' controlling terminal / session before signalling) were not needed.
  Because macOS has no `/proc`, "does the group still have live members" is read from one `ps -A -o pid=,pgid=,stat=` (zombies are ignored; an unreadable listing is `Unknown`, which makes close wait for the grace period and then SIGKILL).
- **launchd**: `deploy/com.misao.daemon.binary.plist` starts the single binary (`__MISAO__ serve`); the Node bundle's `com.misao.daemon.plist` is unchanged. `scripts/smoke-launchd.sh` (CI job `macOS launchd`, a GitHub-hosted runner) renders the template, bootstraps it into `gui/<uid>`, checks `misao status` and a pane, boots it out and checks that the daemon and the pane's child are gone. The systemd unit `misao.service` needs no change: `ExecStart=%h/.local/bin/misao serve` runs the Rust binary when it is installed there.
- Foreground command, `fgCommand`: unchanged (`ps`).
- A race that only showed on macOS (a slower `sh` start): a test sent `pane.close` before the shell had run `trap '' HUP`; it now waits for the child to signal readiness.

### Windows (x64)

Everything is in [Windows](windows.md) section 12. In short: named pipe with the SDK's name and a user-only DACL (`PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE`), ConPTY through portable-pty (the daemon answers its cursor-position query), Job Object for `pane.close`, `PATHEXT` / `.ps1` command resolution with the file name in the error, the repaint filter for `pane.line`, `misao stop` through a user-only named event (the protocol stays 0.3.0), `attach` with the Windows console, and a Task Scheduler definition in `deploy/windows/`.

### Differences from the Node build

- `misao stop` exists only in the Rust build. It is not a protocol method.
- Windows: `pane.open` fails with `command not found: <name>` for a name that `PATH` / `PATHEXT` cannot resolve (Node: `File not found: `, with an empty name); `.ps1` runs; `cmd[0]` without an extension is resolved.
- Windows: the pipe DACL is the launching user only and remote clients are refused (Node: Everyone / ANONYMOUS LOGON can read, reachable over SMB).
- Windows: the data directory is checked for owner and for write grants to broad groups (Node: only symlink and directory).
- Windows: `pane.close` stops the whole tree through a Job Object at once (Node: about 4.7 s and a surviving grandchild).
- Windows: resize repaints are not in `pane.line`.
- All OS: `unsafe_code` is `deny` instead of `forbid` (see above).

## Startup exclusion (difference from the Node build)

The Rust daemon takes an exclusive `flock` on `<socket>.lock` (next to the socket, independent of
`--data`) from the stale-socket check until the socket has been removed on shutdown. So two concurrent
starts cannot remove each other's socket, and a daemon that is still shutting down cannot unlink the
socket of a newer daemon started in the meantime (with a different `--data`, where the pid file does not
exclude them). `Daemon` holds the lock and releases it after removing the socket and the pid file. While a
daemon is alive no other start can take the lock, so the second start fails with "another daemon is already
listening" if the socket answers, and with "another daemon is starting" otherwise (starting or stopping).
A failed `bind` never deletes the path; only a socket whose `chmod` failed after our own `bind` is
removed. The lock file itself is left in place on purpose. The Node daemon does not have this lock: its
check-then-unlink-then-listen sequence can race when two daemons start at the same moment with different
pid-file locations. It is not fixed in the Node build (it is replaced instead).

## Memory and CPU comparison (the #32 conditions)

`scripts/bench-daemon.mjs` measures the daemon's memory (RSS) and CPU with the same pane count, scrollback and output (Linux only; a throwaway daemon, `~/.misao` is untouched).

```bash
npm run build && cargo build --release -p misao
node scripts/bench-daemon.mjs --panes 10,30,60 --patterns quiet,bulk,tui           # default scrollback 5000
node scripts/bench-daemon.mjs --panes 30 --patterns bulk --scrollback 20000         # sensitivity (also --raw-bytes / --lines-bytes)
```

RSS is VmRSS of `/proc/<pid>/status`; CPU is utime + stime of `/proc/<pid>/stat` (the daemon process only, not the panes' children). Output: quiet (none) / bulk (each pane prints about 6.9 MB = 100000 lines at once) /
tui (a Claude Code-like 12-row screen redrawn 10 times a second for 20 s). Panes are 120 x 40. `heapUsed` cannot be read from outside, so RSS is compared. Environment: WSL2, 22 logical cores, a busy dev machine (treat absolute values as a guide).

| Output | Panes | Node at start | Node RSS | Rust at start | Rust RSS | Node CPU time | Rust CPU time |
|---|---|---|---|---|---|---|---|
| quiet | 10 | 72 MiB | 74 MiB | 6 MiB | 8 MiB | 0.1 s | 0.0 s |
| quiet | 60 | 72 MiB | 96 MiB | 6 MiB | 16 MiB | 0.5 s | 0.8 s |
| tui | 10 | 73 MiB | 87 MiB | 6 MiB | 13 MiB | 1.2 s / 20 s | 0.2 s / 21 s |
| tui | 30 | 72 MiB | 119 MiB | 6 MiB | 28 MiB | 2.2 s / 21 s | 0.7 s / 21 s |
| tui | 60 | 72 MiB | 167 MiB | 6 MiB | 51 MiB | 3.7 s / 21 s | 1.9 s / 22 s |
| bulk | 10 | 72 MiB | 444 MiB | 6 MiB | 222 MiB | 6.8 s (done in 6.7 s) | 5.8 s (done in 2.1 s) |
| bulk | 30 | 73 MiB | 1020 MiB | 6 MiB | 651 MiB | 38.8 s (33.5 s) | 39.9 s (6.3 s) |
| bulk | 60 | - | - (not measured to avoid running out of memory) | 6 MiB | 1293 MiB | - | 99.3 s (13.6 s) |

Reading it:
- **Fixed cost**: about 72 MiB for Node (after loading this version's dependencies; more than the 35 MiB in #32) versus about 6 MiB for Rust.
- **Memory per pane**: quiet is small for both (Node 0.4 MiB, Rust 0.2 MiB); TUI is Node 1.5 MiB, Rust 0.7 MiB. With bulk output (scrollback 5000 rows + 4 MiB line ring + 1 MiB raw ring full) it is
  about 32-37 MiB for Node and about 21.5 MiB for Rust (24-byte cells: character + attributes + width + a box for combining marks). Rust stays linear at 60 bulk panes (1.3 GiB).
- **CPU**: total CPU time for the same bulk output is about the same as Node (Rust runs terminal parsing and line assembly on a thread per pane, so **it finishes about 5x sooner**).
  For quiet and TUI panes Rust uses 2-5x less. At 60 quiet panes the cost is mostly starting the panes (pty and child fork), which looks larger for Rust.
  Node is single-threaded: during bulk output it is capped at one core (about 110 %), and RPC replies are delayed meanwhile.

Sensitivity to scrollback and rings (bulk, 30 panes):

| Setting | Node RSS | Rust RSS |
|---|---|---|
| scrollback 1000 | 696 MiB | 313 MiB |
| scrollback 5000 (default) | 1020 MiB | 651 MiB |
| scrollback 20000 | 1874 MiB | 1919 MiB |
| scrollback 5000, `rawBytes` 256 KiB, `linesBytes` 1 MiB | 865 MiB | 498 MiB |

With a large scrollback, Rust's 24-byte cells overtake xterm.js's 12-byte cells (at 20000 rows). There is room to shrink the cell (move combining marks out of the line, put attributes in a table).

## Stage 6: distribution and release

Stage 6 (#44) ships the Rust build as a single binary on GitHub Releases next to the existing Node assets.
The switch of AZITO (its installer, units and bundle) is tracked in AZITO's own issue.

### What a release contains

| Asset | What it is |
|---|---|
| `misao-<version>-<target>.tar.gz` / `.zip` | The Rust binary, one per target (below), with `LICENSE`, `NOTICE` and `THIRD-PARTY-LICENSES.txt` |
| `misao-sdk-<version>.tgz`, `misao-protocol-<version>.tgz` | `@misao/sdk` and `@misao/protocol` (TypeScript, unchanged) |
| `misao-<version>.mjs`, `misao-<version>.LICENSES.txt` | The Node bundle (legacy, see [Retiring the Node assets](#retiring-the-node-assets)) |
| `SHA256SUMS` | sha256 of every asset above |

Targets: `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `aarch64-apple-darwin`,
`x86_64-apple-darwin`, `x86_64-pc-windows-msvc`. Layout of an archive and how to install it:
[Embedding](../embedding.md#the-single-binary) and [deploy/README.md](../../deploy/README.md).

### Build choices

- **Native builds, no cross-compilation.** Each target is built on a runner of its own platform
  (Linux arm64 on `ubuntu-24.04-arm`, macOS Intel on `macos-15-intel`), so the smoke test runs on
  every target. There is no target whose binary is shipped without having been executed.
- **Linux is musl, statically linked.** One binary runs on any distribution with no glibc floor
  (a glibc build would need a documented minimum such as the runner's glibc 2.39). The cost is the
  musl allocator, which is slower and fragments more than glibc's; the e2e suite passes against the
  musl x64 build, and the release smoke test checks that the binary is statically linked.
- **Windows links the C runtime statically** (`-C target-feature=+crt-static`), so the Visual C++
  redistributable is not needed.
- The size and speed settings are the existing `[profile.release]` (thin LTO, one codegen unit,
  `strip`, `panic = "abort"`).
- **Licenses**: `THIRD-PARTY-LICENSES.txt` is generated from the dependency graph with
  [cargo-about](https://github.com/EmbarkStudios/cargo-about) (`about.toml`, `about.hbs`), covering
  all five targets. The accepted licenses in `about.toml` are the same list as in `deny.toml`;
  change both together.
- **Smoke test** (`scripts/smoke-binary.mjs`, run on each target after packing): checks the archive
  layout, that Linux binaries are static, `--version`, `serve` on a temporary socket / pipe,
  `server.info` (`version` equals the release version), creating, reading and killing a pane, and
  `misao stop`. `HOME`, `USERPROFILE` and `MISAO_*` point to a temporary directory.

### Versions

The release tag is the single source of truth. On `main` every version stays `0.0.0`.
`node scripts/set-version.mjs <version>` writes the tag's version (without the `v`) into

- the root and workspace `package.json` files and `package-lock.json`,
- `[workspace.package] version` in `Cargo.toml` and the workspace crates in `Cargo.lock`.

The release workflow runs it before building, in every job that builds anything. The Rust binary
reads its version from Cargo (`CARGO_PKG_VERSION`), so `misao --version` and `server.info.version`
are that value. The smoke test fails if they differ from the version in the archive's name, and
`scripts/verify-release.mjs` does the same for the Node bundle. `protocolVersion`
(`packages/protocol/src/version.ts`) is separate and changes only with the protocol.

### Release procedure

Only a maintainer cuts a release. The workflow publishes on a `v*` tag; the tagged commit must be on `main`.

1. Make sure CI is green on `main` and decide the version (`MAJOR.MINOR.PATCH`, or with a
   pre-release suffix such as `-rc.1`; a hyphen makes it a GitHub pre-release).
2. Optional dry run on the commit to release: Actions > Release > Run workflow, with a version
   such as `0.3.0-rc.0` (see below). Nothing is published.
3. Tag and push: `git tag v<version> <commit on main> && git push origin v<version>`.
4. The workflow builds and verifies the Node assets, builds the five binaries and smoke-tests each,
   assembles the assets, writes `SHA256SUMS` (it fails if a file is missing or unexpected) and
   creates the release. Published assets are never replaced; a fix ships as a new tag.
5. Check the release page, then update the pinned version and sha256 values in the apps that ship misao.

### Dry run

`Release` also runs without publishing, with the same steps up to the assembled assets:

- Actions > Release > Run workflow (`workflow_dispatch`, input `version`, default `0.0.0-dryrun`), and
- on every pull request that touches the release workflow, `scripts/`, `crates/`, `Cargo.toml`,
  `Cargo.lock`, `about.toml` or `about.hbs`.

The assembled files are kept for the default retention period as the artifact `release-assets`.
The `publish` job runs only for a tag push.

### Retiring the Node assets

During the migration every release carries both builds so that an app that still reads
`misao-<version>.mjs` and `misao-<version>.LICENSES.txt` (AZITO's current release pins these names
and hashes) keeps working. The SDK and protocol tarballs are not affected: they stay.

The Node bundle is removed from the release workflow when **both** hold:

1. The apps that ship misao (AZITO) have released a version that uses the binary, and
2. at least two minor releases of misao that carry both builds have been published since the first one.

Then one release drops `misao-<version>.mjs` and its LICENSES file (a separate issue also removes
`packages/daemon`, `packages/cli` and their tests). Until then the Node build is fixed only for
serious defects; new features go to the Rust build.
